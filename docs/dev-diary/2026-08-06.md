## Session — Langfuse v4 back, then replaced by Phoenix everywhere

### What we worked on

Started as "bring Langfuse back" and ended somewhere else. The arc, because the
order matters:

1. Restored Langfuse into the unified compose on **v4** (it was removed
   2026-05-02, `4cfb295`), gated behind a profile, and verified it end-to-end.
   Six things broke on the way; all are written up below.
2. Asked whether aws01 could host it. Answer: yes, but at ~76% memory — too
   close to the 83% that livelocked a host in April. Pushed on that and found
   the real lever was ClickHouse's internal cache config, not the cgroup cap.
   That took the stack from ~3.0 GiB to 1848 MiB.
3. Still not comfortable enough for aws01, so measured Arize Phoenix as an
   alternative: **one container, ~400 MiB**, against the Postgres already
   running.
4. Rejected the split (Langfuse on personal infra, Phoenix on aws01) as two
   systems to debug for one job. **Standardised on Phoenix everywhere**,
   keeping Langfuse behind its profile as a tested fallback.
5. Shipped it to aws01 and verified on the box.

The through-line: nearly every number that mattered was wrong until it was
measured, and two feature claims I made confidently were wrong until I read the
schema.

### What's new upstream

- **v4.6.0**, published 2026-08-06 (the `:4` tag resolves to it; confirmed via
  the image's `org.opencontainers.image.version` label). We were last on
  `v3.169.0`.
- Langfuse was acquired by ClickHouse in Jan 2026. Still MIT, still self-hostable.
- **Architecture is unchanged.** Checked specifically whether v4 dropped the
  heavy dependencies — it did not. ClickHouse is "currently a required
  component… no alternative OLAP database supported." There is no lite/single-
  container mode. Still web + worker + ClickHouse + S3 + Postgres + Redis.
- **v4 raises infra floors:** ClickHouse ≥ 25.12 (we ran 25.3), Postgres ≥ 15
  (we have pg16), Redis ≥ 7.0 (we have 7.4). Only ClickHouse needed moving.
- **Ingestion is now OpenTelemetry.** The legacy batch endpoints and the old
  read APIs are gone. Under v4's default write mode (`events_only`) Python SDK
  ≤v2 and JS/TS SDK ≤v3 are **rejected at ingestion**. The `dual`/`legacy`
  write modes exist only as a migration ramp; a fresh install skips every
  `LANGFUSE_MIGRATION_V4_*` var and lands on `events_only` directly.
- Docs now recommend 4 cores / 16 GiB for a compose deployment and explicitly
  call compose unsuitable for production (no HA, no backups).

### Decisions

The headline one, decided late in the session and reversing the earlier plan:

- **One observability stack on every host, chosen to fit the most constrained
  one.** Phoenix, not Langfuse. A per-host split was considered and explicitly
  rejected — two systems to learn, debug and document for a single job, and the
  "weird" asymmetry is a maintenance tax paid forever. The constrained host
  (aws01) therefore sets the standard for all of them.
- **Langfuse kept, not deleted.** Still in `docker-compose.yml` behind its
  profile, with its database and three volumes intact, so rollback is a profile
  flip. It remains the better answer in two specific cases: MIT licensing, or
  trace volume that outgrows Postgres-backed span storage.
- **Auth on by default for Phoenix.** Upstream ships it off, which leaves the
  UI and the entire API open to anything that can reach the container. Not an
  acceptable default on a shared host.
- **Retention bounded at 90 days.** Upstream defaults to keep-forever, and
  spans land in a Postgres shared with 16 other databases.

The Langfuse-specific decisions below still stand, since that profile is kept:

- **`profiles: [langfuse]`, opt-in per host.** This is the direct answer to why
  it got removed last time: a fresh clone silently inherited a 4-container,
  multi-GiB stack. Now nothing starts unless a host asks for it.
- **Namespaced `langfuse-clickhouse` / `langfuse-minio`.** Not cosmetic — see
  the MinIO collision below.
- **Volumes default to `langfuse_`-prefixed names.** The v3-era `clickhouse_data`
  / `minio_data` volumes are left untouched on disk rather than migrated or
  deleted; the Postgres side had 0 projects and 0 API keys, so everything in
  them was already unreachable. `CLICKHOUSE_VOLUME`/`MINIO_VOLUME` can point
  back at them if that ever turns out to be wrong.
- **Pin V8's heap explicitly instead of chasing `mem_limit`.** See below.
- **aws01 gets its own copy, in its own repo.** aws01 no longer runs this repo
  at all (details below), so it's a separate change against `aws01-stack`.

### Issues encountered

**1. `${VAR:?}` guards break every host, not just Langfuse hosts.**
Wrote the three no-safe-default secrets as `${LANGFUSE_ENCRYPTION_KEY:?…}` so
compose would fail loudly. It fails loudly for *everyone*: interpolation is
evaluated at parse time even for services whose profile is inactive, so
`docker compose config` — and `deploy.sh`'s bare `docker compose up -d` — broke
on hosts with no Langfuse at all. Exactly the fresh-clone breakage that got the
stack removed in May, reintroduced by the guard meant to prevent misconfiguration.
Moved the check into `start.sh`, where it can be conditional.

**2. Langfuse would have written its blobs into TheCollective's MinIO.**
TheCollective's storage stack runs a container named `minio` on the *shared*
`infra` network, holding the `minio` DNS alias. A service named `minio` in this
compose resolves `http://minio:9000` to *that* container — wrong bucket, wrong
credentials, another project's object store. Caught by a container-name conflict
on startup, but the DNS half would have been silent. Renamed to
`langfuse-minio` / `langfuse-clickhouse` and repointed every endpoint.

**3. v4's worker needs ~4× the memory v3's did.**
Carried the v3 caps over unchanged. `langfuse-worker` crash-looped on exit 134
(SIGABRT): it completes its migrations and evaluator/dashboard seeding, then
dies with "Ineffective mark-compacts near heap limit" at a ~248 MB heap. The
512m cap that held for the v3 worker yields a ~256 MB V8 old-space ceiling, and
v4's worker startup exceeds it. Session 16's lesson applied to `langfuse-web`;
it now applies to the worker too.

**4. Then `langfuse-web` did the same thing one notch higher.**
Raised the worker, and web began crash-looping — 15 restarts, exit code 0
(V8 aborts, the entrypoint script exits cleanly, `restart: always` loops it),
dying at a ~756 MB heap under the 1536m cap that fixed this exact problem under
v3. This is the trap in the auto-derivation: raise the cap, V8 raises the heap,
the app fills the heap, it dies again. Fixed properly by pinning
`NODE_OPTIONS=--max-old-space-size=2048` and setting the cap ~25% above it, so
both numbers mean something independently.

**5. The healthcheck could never have passed.**
`wget http://localhost:3000/...` inside the container returned "Connection
refused" while the app served fine on the published port. Next.js 16 binds the
server to the *container hostname*, not loopback — the boot log says
`Local: http://<container-id>:3000`. Changed to `http://$$HOSTNAME:3000`.

**6. …and the broken healthcheck was why Traefik 404'd.**
`https://langfuse.localhost` returned a bare 404 with no router in Traefik's
API and nothing in its log, while `localhost:3030` worked. Traefik v3's Docker
provider does not publish a router for a container that isn't healthy. Fixing
the healthcheck made the router appear immediately. Worth remembering: *a
missing @docker router with correct labels means look at container health*.
(Also removed the `certresolver=${…:-}` label — an empty certresolver silently
invalidates a router. Umami has the identical latent bug; it's gated off and
prod sets a real value, so it was left alone.)

### Measured footprint — and why the first number was wrong

Initially reported ~2.2 GiB from a single `docker stats` sample taken minutes
after boot. That understated it twice over, and re-measuring with cgroup
`memory.peak` (not an idle sample) corrected both errors:

**ClickHouse's `mem_limit` is a RESERVATION, not a ceiling.** It reads the
cgroup limit, sets `max_server_memory_usage` to 0.9x it, and then fills
mark/uncompressed caches (configured at 5 GiB / 8 GiB) until it gets there and
stays. Measured at 651 MiB, then 1029 MiB ten minutes later, heading for its
1.35 GiB self-limit under a 1536m cap. Given an 896m cap it settles at 883 MiB.
Whatever you give it, it takes. That makes the ClickHouse cap the single
biggest sizing lever on this stack.

**Node's boot peak is ~60% above its steady state.** `langfuse-web` idles at
~1.0 GiB but peaks at 1.6 GiB during Next.js boot. Sizing from an idle sample
is precisely the Session 16 mistake.

| container | resident | peak | default cap | tuned cap |
|---|---|---|---|---|
| langfuse-web | ~1.0 GiB | ~1.6 GiB | 2560m | 1792m (heap 1280) |
| langfuse-worker | ~0.5 GiB | ~0.6 GiB | 2g | 1g |
| langfuse-clickhouse | = its cap | = its cap | 1536m | 896m |
| langfuse-minio | ~0.12 GiB | ~0.12 GiB | 512m | 256m |

**Defaults: ~3.0 GiB resident / ~3.4 GiB peak. Tuned: ~2.5 / ~2.9 GiB.** The
tuned config was verified stable — 0 restarts across all four containers over
4 minutes, health endpoint green, and an OTLP span ingested and read back out
of ClickHouse. Caps are now per-host tunable via `LANGFUSE_*_MEM`.

### Follow-up: cutting the footprint, and Phoenix for aws01

**Langfuse got a lot smaller.** The cgroup cap was never the real lever —
ClickHouse's internal caches were. Its defaults advertise a 5 GiB mark cache,
8 GiB uncompressed cache, and 5 GiB each of index-mark and primary-index cache,
because it assumes it owns the machine. Added `clickhouse/low-memory.xml`
(mounted into `config.d/`) setting those to 256 MiB / 0 / 128 / 128 with an
explicit 640 MiB `max_server_memory_usage`, and dropped ClickHouse's internal
telemetry tables (`metric_log`, `trace_log`, `asynchronous_metric_log`,
`query_thread_log`, `text_log`) which were also growing on disk forever.

ClickHouse went from ~1.35 GiB to **378 MiB anon**. Whole stack: ~3.0 GiB →
**1848 MiB**. Caps came down with it (web 2560m→1536m, worker 2g→896m,
clickhouse 1536m→896m, minio 512m→256m). Re-verified at those settings: 0
restarts, healthy, span ingested and read back.

Also corrected a measurement error along the way: cgroup `memory.current`
includes reclaimable page cache. Splitting `anon` from `file` in `memory.stat`
is the number that reflects real pressure.

**Then: Phoenix everywhere, not just aws01.** Running Langfuse on personal
infra and Phoenix on aws01 was two systems to learn and debug for one job. The
call was to standardise on the option that fits the most constrained host, so
Phoenix is now the default in this repo too (profile `phoenix`), and Langfuse
stays behind its profile as a documented, tested fallback rather than the
default anywhere. Local was cut over and verified: traefik router published,
UI + /healthz 200 through TLS, 401 unauthenticated / 200 with bearer, span
ingested via the in-cluster `http://phoenix:6006` alias, 392 MiB resident.

**The footprint case for aws01.** Measured both on this machine with the
same OTLP payloads rather than trusting comparison posts:

| | containers | resident | external deps |
|---|---|---|---|
| Langfuse v4 (tuned) | 4 | 1848 MiB | Postgres + Redis + ClickHouse + S3 |
| Arize Phoenix 19.18.0 | 1 | ~400 MiB | Postgres (already running) |

Phoenix ingested 500 spans under a 1g cap at 411 MiB with no OOM and no
restarts. On aws01 that is ~42% of the box versus ~61%, which is the difference
between "works" and "comfortable" on a host that also carries ~1.4 GiB of
IT-managed agents.

**Correction: Phoenix does NOT give up cost tracking or prompt management.**
I asserted twice during this session that it did, and used that as a stated
cost of switching. That was wrong, and it was an input to the decision. Checked
against the live schema afterwards:

- `generative_models` — 268 rows; `token_prices` — 797 rows, with separate
  `input`, `output`, `cache_read` and `cache_write` rates per model. The
  catalog knows `claude-opus-5`, `claude-sonnet-5`, `gpt-5` and `gpt-5.4`, so
  it covers the very gap (`totalCost: 0` on current models) that forced the
  Langfuse v2 -> v3 migration back in April.
- `prompts`, `prompt_versions`, `prompt_version_tags`, `prompt_labels` —
  versioning and labels, the same shape as Langfuse's prompt management.
- `datasets`, `dataset_versions`, `experiments`, `experiment_runs`,
  `builtin_evaluators` — evals and experiments are there too.

Lesson: "lightweight alternative" framing in comparison write-ups is not a
feature inventory. Reading the schema takes one query and would have prevented
stating a false trade-off twice.

Genuine remaining trade-offs:
- **Licensing.** Phoenix is Elastic License 2.0, not OSI open source; Langfuse
  core is MIT. No practical constraint for internal use, but real.
- **Scale ceiling.** Phoenix stores spans in Postgres. ClickHouse exists in
  Langfuse precisely because Postgres stops keeping up at high trace volume.
  Nowhere near that here, but it is the thing that would force a revisit.

Phoenix gotchas found by testing, not reading:
- **The image is distroless.** No `sh`, no `wget`, no `curl` — a `CMD-SHELL`
  healthcheck fails with "executable not found" and the container never reports
  healthy. Only the exec form works, with `python` as the one interpreter present.
- **OTLP/HTTP wants protobuf**, not JSON. The same JSON payload Langfuse
  accepted returns HTTP 415 here.
- **Auth is off by default** — without `PHOENIX_ENABLE_AUTH` the UI and API are
  open to anything on the network. Enabled, with `/healthz` left unauthenticated
  so the healthcheck still works.
- **Retention defaults to keep-forever** (`0`). Set to 90 days; nothing else
  prunes the spans table.

### Where the data lives

Phoenix persists **everything** to the shared Postgres, in its own `phoenix`
database — 62 tables, 12 MB with one project: spans, projects, users and roles,
datasets, experiments, prompts, and the model price catalog.

The `phoenix_data` volume (`PHOENIX_WORKING_DIR`) is **0 bytes** — empty
`inferences/`, `trace_datasets/`, `wasm/` scaffolding. It only carries data in
SQLite mode. Postgres itself persists to `postgres_data` as before.

Two consequences worth stating plainly:
- Whatever backs up Postgres now covers Phoenix. No separate backup path.
- Phoenix's span growth lands in the same Postgres as `librarian` (182 MB),
  `marie`, `caitie_db`, `hub` and 13 other databases. The 90-day retention
  policy is what keeps that bounded — upstream's default is keep-forever.

The old `langfuse` database (13 MB) and the three `langfuse_*` volumes are
retained untouched, so re-enabling that profile picks up where it left off.

`deploy.sh` recreates the infra and app containers as part of its reconcile, so
everything except `puncher-*` restarted during the run and came back healthy.
Worth knowing before running it during anything sensitive.

**A bug in my own change, caught before it bit.** The deploy guard I wrote keyed
only on `phoenix/.env` existing. But the natural bootstrap order is *generate
secrets on the box, then merge and pull* — and in that window `.env` exists
while `phoenix/docker-compose.yml` does not. `docker compose -f
phoenix/docker-compose.yml pull` would then run against a missing file and,
under `set -e`, **abort the entire deploy**, taking newsintel, company_intel and
puncher's reconciliation with it. Fixed to require both, and simulated the
window to confirm it skips cleanly. Generalisable: an opt-in guard should test
for the thing it is about to *use*, not for the thing that signals intent.
